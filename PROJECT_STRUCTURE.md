# Project Structure and Functioning

## 1. File Structure

### Python Scripts
*   **`main.py`**: The entry point of the application. It orchestrates the sequence of operations: loading data, processing transactions, and generating reports.
*   **`classes.py`**: Defines the core data models:
    *   `Bank`: Tracks global statistics (total transactions, deposits, withdrawals, etc.).
    *   `BankAccount`: Represents an individual customer account with methods for deposit, withdraw, and transfer.
    *   `Transaction`: Represents a single transaction record.
*   **`functions.py`**: Contains the operational logic. It handles file I/O (reading/writing CSVs), data validation, and formatting output.
*   **`storage.py`**: Acts as a shared memory state. It initializes the `Bank` object and holds the dictionary of transactions during runtime.

### Data Files (CSV)
*   **`balance.csv`**: Stores the current state of all bank accounts (Account Number, Name, Balance).
*   **`previous_report.csv`**: Contains the summary statistics from the previous day.
*   **`transaction.csv`**: The input file containing the list of transactions to process for the current day.
*   **`today_report.csv`**: The output file generated by the system containing the summary statistics for the current day.

## 2. System Functioning

The system operates in a linear pipeline:

### Step 1: Initialization & State Loading
1.  The system starts in `main.py`.
2.  It reads `previous_report.csv` to load the bank's historical financial metrics (Net Amount, etc.).
3.  It resets daily counters (e.g., `total_transactions` for the day) to zero to prepare for a new processing cycle.

### Step 2: Account Loading
1.  The system reads `balance.csv`.
2.  It populates the `Bank` object with `BankAccount` instances.
3.  This establishes the starting balance for every customer before any new transactions occur.

### Step 3: Transaction Processing
1.  The system reads `transaction.csv` row by row.
2.  **Validation**: It checks if:
    *   The Transaction ID is unique.
    *   The Transaction Type is valid (deposit, withdraw, transfer).
    *   The Source Account exists.
3.  **Execution**:
    *   If valid, the specific operation is performed on the `BankAccount` objects.
    *   If invalid (e.g., insufficient funds, wrong account number), the transaction is marked as "Fail".
4.  **Tracking**: The `Bank` object updates its global counters (Success/Fail counts, Total Amounts) in real-time.

### Step 4: Reporting & Persistence
1.  **Daily Report**: The system writes the calculated daily statistics to `today_report.csv`.
2.  **Balance Update**: The updated balances of all accounts are written back to `balance.csv`, overwriting the old values.
3.  **Console Display**: A comparison table is printed to the terminal, showing the difference between "Yesterday's" stats and "Today's" stats.

## 3. Future Scope

The project is designed to be modular, allowing for easy addition of new features:
*   **Invalid Transaction Reporting**: A function can be added to log and display details of failed transactions.
*   **Extended Functionality**: Features like graphical visualizations, database integration, and detailed audit logs can be implemented in future updates.
